# mruby/c WebAssembly Sample

This repository is a small, browser-focused sample that compiles Ruby 4.0-compatible source code with mruby's bytecode compiler and then runs the generated bytecode with the mruby/c virtual machine.

The project is intentionally educational. It shows how two independent WebAssembly modules can cooperate from JavaScript:

1. `mrbc.js` compiles Ruby source code into `.mrb` bytecode.
2. `mrubyc.js` executes that bytecode with the mruby/c VM.
3. `public_html/app.js` connects the compiler, the VM, and the browser UI.

The default build targets Web browsers with Emscripten's `web` environment. The same architecture can also be adapted for Node.js-based tooling, including VS Code extensions, but that requires a Node-compatible Emscripten build and different `.wasm` file loading.

## What You Can Learn from This Sample

- **Running a compiler in the browser**
  `mrbc.js` is an Emscripten build of `mruby-bin-mrbc`. The browser app calls the compiler entry point directly from JavaScript.

- **Passing binary data between WebAssembly modules**
  The generated `.mrb` bytecode is read from the compiler module and copied into the mruby/c module's heap.

- **Embedding mruby/c behind a small C bridge**
  `src/main.c` exposes a compact WebAssembly API for initializing the VM and running bytecode.

- **Serving generated WebAssembly artifacts from a plain static site**
  The browser sample is only HTML, CSS, JavaScript, and `.wasm` files under `public_html/`.

## Quick Start

The repository includes generated browser artifacts under `public_html/mrbc/` and `public_html/mrubyc/`, so you can serve the sample without rebuilding the toolchain first.

Start a local HTTP server:

```sh
make serve
```

Open:

```text
http://localhost:8000/
```

Enter Ruby code, press **Compile and Run**, and the output will appear in the page.

If port `8000` is already in use, choose another port:

```sh
make serve PORT=3000
```

Do not open `public_html/index.html` directly through `file://`. Most browsers restrict WebAssembly module loading from local files, so the sample should be served over HTTP.

## WebAssembly Runtime Notes

- **Serve the sample over HTTP**
  Do not open `public_html/index.html` directly from the local filesystem. ES module imports and WebAssembly loading are URL-based, and browsers commonly block or restrict `.wasm` loading from `file://` pages. Use `make serve` or another local HTTP server.

- **Serve `.wasm` files with an appropriate MIME type**
  For production hosting, configure the server to return `Content-Type: application/wasm` for `.wasm` files. The local `make serve` target uses Python's static HTTP server, which works for this sample.

- **Keep generated files and paths together**
  `public_html/app.js` uses `locateFile` callbacks so that `mrbc.wasm` is loaded from `public_html/mrbc/` and `mrubyc.wasm` is loaded from `public_html/mrubyc/`. If the files are moved, update those paths together.

- **Use a modern browser**
  The generated artifacts are Web-targeted Emscripten modules and are intended for modern browsers with WebAssembly and ES module support.

- **Check Content Security Policy settings when embedding**
  If this sample is embedded into a stricter site or Webview, the host Content Security Policy must allow WebAssembly compilation and loading of the generated `.js` and `.wasm` files.

- **Treat this as a sample runtime, not a hardened sandbox**
  WebAssembly isolates linear memory, but Ruby code still runs inside the browser page's process and can consume CPU or memory. Do not treat this sample as a complete security boundary for untrusted or long-running programs.

## Requirements

### For Running the Included Browser Sample

- **GNU Make**
  Used by `make serve`.

- **Python 3**
  Used by the `make serve` target through `python3 -m http.server`.

### For Rebuilding the WebAssembly Artifacts

- **Emscripten SDK 5.0.7**
  The default `EMSDK_VERSION` is `5.0.7`.

- **Ruby 4.x**
  Required by mruby and mruby/c generator scripts. The default configuration expects Homebrew Ruby at `/opt/homebrew/opt/ruby/bin/ruby`.

- **mruby 4.x**
  The checked-out mruby submodule must report `MRUBY_RELEASE_MAJOR` as `4` and `MRUBY_RUBY_VERSION` as `"4.0"`.

- **mruby/c**
  The mruby/c submodule is compiled with the Emscripten HAL.

## Building from Source

Initialize submodules if they have not been checked out yet:

```sh
git submodule update --init --recursive
```

Install and activate the expected Emscripten SDK version:

```sh
make emsdk-install
source emsdk/emsdk_env.sh
```

Check that `emcc` is available:

```sh
emcc --version
```

Validate the Ruby and mruby requirements:

```sh
make check-ruby4 check-mruby4
```

Build both WebAssembly modules:

```sh
make
```

This is equivalent to:

```sh
make mrbc
make mrubyc
```

The build writes the browser artifacts to:

- `public_html/mrbc/mrbc.js`
- `public_html/mrbc/mrbc.wasm`
- `public_html/mrubyc/mrubyc.js`
- `public_html/mrubyc/mrubyc.wasm`

If Ruby 4.x is installed outside the default Homebrew path, pass both the executable path and the directory that should be placed first in `PATH`:

```sh
make RUBY=/path/to/ruby HOMEBREW_RUBY_BINDIR=/path/to
```

## How the Browser Sample Works

### 1. Loading the Modules

`public_html/app.js` imports both generated Emscripten modules as ES modules:

- `./mrbc/mrbc.js`
- `./mrubyc/mrubyc.js`

Each module is created with a `locateFile` callback so that the corresponding `.wasm` file is loaded from the correct subdirectory.

### 2. Compiling Ruby Source with `mrbc.js`

When the user clicks **Compile and Run**, the app writes the editor contents into Emscripten's virtual filesystem as `input.rb`.

It then builds an `argv` array in WebAssembly memory and calls the compiler entry point as if it had run:

```text
mrbc -o input.mrb input.rb
```

After `_main()` returns successfully, the app reads `input.mrb` from the compiler module's virtual filesystem. That file is the mruby bytecode that will be passed to mruby/c.

This is why `mrbc.js` exports:

- `_main`
- `_malloc`
- `_free`
- `stringToUTF8`
- `setValue`
- `FS`

### 3. Running Bytecode with `mrubyc.js`

The mruby/c module is initialized once by calling:

```text
_mrbc_wasm_init()
```

For each run, the app:

1. Allocates memory inside the mruby/c WebAssembly module.
2. Copies the compiled bytecode into `HEAPU8`.
3. Calls `mrbc_wasm_run()` through Emscripten's `ccall()`.
4. Frees the bytecode buffer after execution.

`src/main.c` implements the exported bridge. It validates the bytecode size and header, creates an mruby/c task, runs the scheduler, flushes output, and resets the VM so that the next execution starts from a clean state.

## Build Configuration Notes

The UI is deliberately small, but the Emscripten settings are important because JavaScript calls directly into both generated modules.

### `mrbc.js`

`mrbc.js` is built from `mruby-bin-mrbc` using `mruby_build_config.rb`.

Important settings include:

- **`-sENVIRONMENT=web`**
  Builds browser-targeted output. The generated artifact is not intended to run directly in Node.js.

- **`-sMODULARIZE=1` and `-sEXPORT_ES6=1`**
  Emits an ES module factory that can be imported from `public_html/app.js`.

- **`-sEXPORT_NAME=createMrbcModule`**
  Gives the generated factory a stable JavaScript name.

- **`-fwasm-exceptions` and `-sSUPPORT_LONGJMP=wasm`**
  Support the exception and long-jump behavior required by the mruby build.

- **`-sFORCE_FILESYSTEM=1`**
  Enables Emscripten's virtual filesystem because the compiler reads `input.rb` and writes `input.mrb`.

- **`-sINVOKE_RUN=0`**
  Prevents the compiler from running automatically when the module loads. The browser app calls `_main()` explicitly.

- **`-sEXPORTED_FUNCTIONS=["_main","_malloc","_free"]`**
  Exposes the compiler entry point and memory management functions used by JavaScript.

- **`-sEXPORTED_RUNTIME_METHODS=["stringToUTF8","setValue","FS"]`**
  Exposes the runtime helpers needed to construct arguments and access files.

### `mrubyc.js`

`mrubyc.js` is built directly with `emcc` from mruby/c sources, the Emscripten HAL, and `src/main.c`.

Important settings include:

- **`-sENVIRONMENT=web`**
  Builds browser-targeted output for the static sample.

- **`-sMODULARIZE=1` and `-sEXPORT_ES6=1`**
  Emits an ES module factory that can be imported independently from the compiler module.

- **`-sEXPORT_NAME=createMrubycModule`**
  Gives the generated factory a stable JavaScript name.

- **`-DMRBC_SCHEDULER_EXIT=1`**
  Allows `mrbc_run()` to return to JavaScript after the task finishes.

- **`-DMRBC_MEMORY_SIZE=131072`**
  Defines the memory pool used by mruby/c in `src/main.c`.

- **`-sFILESYSTEM=0`**
  Keeps the VM module smaller because it receives bytecode through memory instead of Emscripten's filesystem.

- **`-sASYNCIFY=1`**
  Supports the Emscripten HAL behavior used by mruby/c.

- **`-sEXPORTED_FUNCTIONS=["_mrbc_wasm_init","_mrbc_wasm_run","_malloc","_free"]`**
  Exposes VM initialization, bytecode execution, and memory management functions.

- **`-sEXPORTED_RUNTIME_METHODS=["ccall","HEAPU8"]`**
  Exposes the runtime call helper and heap view used by `public_html/app.js`.

- **`--no-entry`**
  Builds a module that is called from JavaScript instead of a standalone program with a native `main()`.

## Using the Same Idea from Node.js or a VS Code Extension

The checked-in artifacts are Web-targeted. They are appropriate for a browser page and for a VS Code Webview, where code runs in a browser-like environment.

For a Node.js extension host or another non-browser runtime, rebuild the modules with an Emscripten environment that includes Node.js support, such as `node` or `web,node`, and resolve the generated `.wasm` files from the extension or package installation directory.

The high-level flow stays the same:

1. Instantiate the compiler module.
2. Compile Ruby source into `.mrb` bytecode.
3. Instantiate the mruby/c VM module.
4. Copy the bytecode into the VM module's memory.
5. Call the exported run function.

## Troubleshooting

### `emcc was not found`

The Emscripten environment is not active in the current shell.

Run:

```sh
source emsdk/emsdk_env.sh
```

### `Ruby 4.x is required`

The Ruby executable used by the Makefile is not Ruby 4.x.

Use Homebrew Ruby 4.x or pass the Ruby path explicitly:

```sh
make RUBY=/path/to/ruby HOMEBREW_RUBY_BINDIR=/path/to
```

### `Ruby 4.x must be first in PATH for mruby/c generator scripts`

Some mruby/c generator scripts use `#!/usr/bin/env ruby`. Set `HOMEBREW_RUBY_BINDIR` to the directory that contains the intended Ruby 4.x executable.

### `mruby 4.x is required`

The `mruby` submodule does not match the required major version. Check the submodule state:

```sh
git submodule status
```

### The browser cannot load `.wasm`

Serve the sample over HTTP:

```sh
make serve
```

Also check that each `locateFile` callback returns the correct path for its `.wasm` file.

### Output from one run affects the next run

`src/main.c` resets the mruby/c VM after each execution by calling `mrbc_cleanup()` and initializing the VM again. If state still appears to leak between runs, check whether JavaScript code is bypassing the normal `mrbc_wasm_run()` flow.

## Limitations

- **The UI is intentionally minimal**
  The sample is a demonstration of the compile-and-run pipeline, not a full Ruby editor or IDE.

- **Bytecode size is limited**
  `src/main.c` currently rejects bytecode larger than `1024 * 1024` bytes.

- **The mruby/c memory pool is limited**
  The Makefile currently defines `MRBC_MEMORY_SIZE=131072`.

- **The checked-in artifacts are browser-targeted**
  Direct Node.js usage requires a Node-compatible Emscripten environment setting.

- **Ruby code can still consume browser resources**
  This is a sample runtime. It is not a hardened sandbox for untrusted, long-running, or resource-intensive programs.
